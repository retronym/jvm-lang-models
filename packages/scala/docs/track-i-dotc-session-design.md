# The dotc interactive session: design notes

Design doc for the spike in [`dotc-session.patch`](../../../docs/upstream/dotc-session.patch) ([retronym/scala3#68](https://github.com/retronym/scala3/pull/68), draft): what the presentation compiler's driver does per request after the patch, why it is shaped that way, what the alternatives were, and what the measurements and the suites found. It stands alone; [track-i-scala3-cancellation.md](track-i-scala3-cancellation.md) is the history (the survey that led to the cancellation design, the first session spike), and [track-i.md](track-i.md) the model this is an instance of. The x-ray page in [`probes/interrupt/xray`](../probes/interrupt/xray) shows every number below live.

## Summary for a busy reader

A request to the presentation compiler (a completion, a hover) used to cost a fresh run that typed the whole file, could not be cancelled once the typer had started, and was lost whole if a cyclic reference surfaced anywhere in it. After the patch:

- **The typer types only the path to the request.** Of each statement list on the way down (the package's top-level statements, each class body), only the statement containing the target span is typed; the others are recorded, untyped, with the context they would have been typed in. On the x-ray's 60-object file a completion in object 10 types 43 trees instead of 791; on the suite's 400-object file, 2 top-level trees instead of 22, with 400 statements and members skipped.
- **One run serves a session.** Requests on unchanged content reuse the run: a target inside what is typed is answered without typing anything; a target inside a skipped statement types that statement, in its recorded context, in the same run, and splices the result into the typed tree. The run's denotations, completers and caches stay valid throughout. An edit starts a fresh run, which is now cheap.
- **A cancellation unwinds, and lands where it should.** The typer polls every 1,024 trees and unwinds with `CancelledCompilation`; the driver survives and keeps everything typed before the abort. A statement whose typing was unwound cannot be typed again (its untyped tree is consumed, finding I8), so it is re-parsed and re-indexed in place and skipped again. The x-ray's `Latch.await` macro blocks the typer at a known point so that a cancellation can be demonstrated deterministically.
- **Degrade instead of failing.** In interactive mode a cyclic reference, a stack overflow or an assertion inside one completion costs that one symbol, not the request (the provider's per-item handlers already did this for member completions); the `Touched` flag no longer leaks from an unwound completion, a stale one is healed instead of reported as a cycle, and only a run that met an exception of unknown effect is *tainted* (the next request starts fresh). That is IntelliJ's `RecursionManager` discipline (`doPreventingRecursion`, `markStack`/`mayCacheNow`) mapped onto `completeFrom`; §6 has the measurements that sized it: one cycle in 1,074 completions over `Typer.scala` and `Namer.scala`, and 223 over the whole suite, nearly all in the provider's own type-ahead.

## 0. Why this is easier to reason about than scalac's presentation compiler

scalac's interactive compiler (`src/interactive`, [track-i.md](track-i.md) §2) runs a background thread that typechecks every open unit, and services a request *inside* that work: the typer calls `signalDone` after each tree, the request's targeted typecheck (`typedTreeAt`, with `unit.targetPos`) runs at that safepoint on the same mutable trees and symbol table the background was halfway through, and the background resumes afterwards from whatever the request left. Correctness is then a statement about interleavings: for every safepoint the background can be at when a request arrives, the answer must equal the answer a request after the background would get. Track I's harness injects a request at every safepoint of a toy with scalac's mechanisms; before [scala/scala#11328](https://github.com/scala/scala/pull/11328) the four scenarios modelled on the PR's tests diverged at 8–13 of 14–18 safepoints, and the PR's four fixes are each a property restored across an interleaving: a synthesis burst made uninterruptible, synthetics kept for a targeted check, a factory symbol kept rather than replaced, warnings left suspended ([track-i.md](track-i.md) §4). The state being protected is shared and mutable: trees typed in place (`setType`, `symbol =`), `unit.synthetics`, the `locked` flag reset in a `finally`, symbols re-entered by `enterExistingSym`. Every fix is local to one shape, and the harness is the only way to know there is no fifth.

The design here has no interleaving to reason about. The units of consistency are:

- **A statement, typed or not.** Typed trees are immutable values; a statement is either in the typed set (a value, never touched again) or in the skipped list (untyped, its context recorded, nothing of it computed). There is no "half typed by the background" state for a request to land in: the targeted run *omits* the other statements instead of typing them concurrently, and a resume types one in the same context the in-order traversal would have used (§2, §3). The toy's dotc kernel diverges at zero safepoints by construction for this reason ([track-i.md](track-i.md) §4).
- **A run.** Denotations, completers, caches and constraint state belong to one run; a request on unchanged content stays in it, an edit discards it whole and starts another, cheap because targeted. What outlives a run is explicit and short: classpath symbols (loaders that can be re-run), and the facts §3 forces before a file is left (I17). scalac's `TyperRun` is reused across requests with the same shared symbols, and which facts outlive which run is implicit.
- **A request.** Cancellation unwinds to the request boundary (§4): what it leaves is per-run state the next request can recompute, plus the one global flag, `Touched`, cleared on the way out (§6). scalac's `CancelException` unwinds through the background check, so the invariants have to be re-established by `finally` blocks and the next retype.
- **Degradation.** A cycle costs one symbol for one request, the symbol stays completable, and nothing computed under the prevention is kept (§6). scalac marks the symbol `LOCKED` for the duration of the completion and relies on the unlock; the model's [`touched_stays_cyclic`](../../query/Query/Interrupt.lean#L287) versus [`forceA_unlock_touched`](../../query/Query/Interrupt.lean#L315) ([track-i.md](track-i.md) §11) is that difference.

So the checks are different in kind. scalac's needed an interleaving harness, one interleaving per safepoint, and found each bug by its shape. This design is checked by comparison with the whole-file answer under *any* sequence of requests, cancellations and edits (`CompletionSoakSuite`, §3): the invariant is "the typed set is a subset of what a whole-file run would type, with the same values", and the soak is a random walk over sequences, not interleavings. The three things that still need care are the places where immutability is not quite true, each named as a finding and handled: an untyped tree is consumed by typing (I8: re-parse the statement), a completer refuses to run in a later run (I7, I17: force before leaving the file), and typing a sibling used to be relied on for symbol-side facts (I13: completers and `children` made sufficient). None is an interleaving.

## 1. The problem

Metals runs dotc's `InteractiveDriver` on the file being edited. Each request made a new `Run`, parsed the file, indexed it (the Namer creates one symbol per definition, with a completer that computes its type lazily) and typed every statement of it, then answered from the typed tree. Three things are wrong with that for an editor:

1. **Most of the typing is for nothing.** A completion in the body of one method needs that method's typed body and the *signatures* of what it refers to. The signatures come from completers, lazily; the bodies of every other method are typed only because `typedStats` walks the file in order. Finding I9's scaling table has the cost growing linearly with the file.
2. **Nothing survives between requests.** The next request on the same content starts over: new run, new symbols, new completers, the previous run's work discarded, although immutable typed trees are pure values keyed by nothing.
3. **A run cannot be stopped, and failure is all or nothing.** The driver's cancellation hook consumed the thread's interrupt bit and never unwound the typer, so a request made obsolete by the next keystroke ran to completion and the next request queued behind it. A `CyclicReference` thrown from a completer anywhere in the run, or a stack overflow, unwinds the request; the presentation compiler catches it and returns an empty answer. Worse, a lazy computation unwound by an exception can leave its symbol marked `Touched`, so that every later request in the same run sees a spurious cycle.

§2 and §3 are the first two problems; §4 is cancellation, the one exception the typer is now made to unwind on; §6 generalises the unwinding to the failures a request meets on its own.

## 2. Targeting: type only the path

`Run.typingTarget` is the request's span. `Typer.typedStats` is where statements of a package or a template are typed in order, so it is where the decision is made. The rule, for one statement list:

- If no statement of the list contains the target (the target is in a class header, or in a comment between definitions), only the first statement *after* the target is typed. scalac's rule (`Typers.typedStats`: "skip typechecking of statements in a class or module that don't include the target position", applied only when some sibling does include it) types the whole list in that case, and the first version of this spike did the same; the x-ray's hover mode showed the cost: a hover on `class JavaParser`'s header typed all of its members, 10,000 trees for one request. What that case needs is the definition the comment documents, the *next* sibling, and nothing else.
- Otherwise every statement that does not contain the target is skipped: recorded on the run as `SkippedStat(stat, ctx, owner)`, the untyped tree with the context it would have been typed in and the statement owner (the package class, or the template's local dummy), and left out of the typed tree.
- Only statements of the request's own source are subject to the rule (`ctx.source` is the compilation unit's source). The trees of an inlined macro body are re-typed by the same typer and carry the macro's source, and a span is an offset *in its source*: the first version compared those spans with the request's offset and skipped the splice body's `$anonfun` whenever the offset fell outside it, which made a macro expand or not with the length of the file (finding I19).
- Never skipped: imports and exports (they shape the context of what follows), nested package clauses (containers; their own statements are subject to the rule), and trees without a source range of their own (the module val the Namer expands an `object` into, a synthetic companion: cheap, and nothing could target them).
- The statements of blocks are subject to the rule too (`typedBlockStats` marks its list, with `Run.targetedStatsInBlock`), since a block's local symbols are indexed with completers like a template's: a statement before the target is typed only if the target's statement refers to it, so a macro in an earlier statement is expanded only when something depends on it (the x-ray's latch is now a dependency of the statement at the cursor, not a toll on the way to it). Two refinements the suites forced. A chain of dependent locals typed through their completers is recursion (200 dependent vals overflowed the stack), so the statements before the target that it depends on *by name*, transitively (a conservative footprint, the shape of Track I's tree model), are typed in order rather than skipped. And a skipped definition leaves a typed *stub* in the `Block`, its name and symbol with no body, because the presentation compiler rebuilds a block's scope from the typed statements (`Interactive.contextOfPath` enters every `MemberDef`'s symbol): without the stubs `locally { val x = 1; x@@ }` lost `x`. The stub's info stays lazy. A request that lands in a skipped block statement resumes the run too: the statement is typed in the block's recorded context and inserted, in source order, into the innermost typed `Block` whose span contains it, in place of the stubs it left (an expression statement left none). The first version resumed without splicing, so the stub was served (finding I20: a hover in a `while` body found the block, a completion there found nothing; the oracle suite found it in every file within a dozen requests); the second took a fresh run for such a target, which made every hover on a sibling statement inside a method a new run, 506 fresh runs per 1,200 oracle requests on `ByteCodecs`; the splice brings that to 3, and the session's 1,200 requests from 1.3 s to 0.28 s. And a block is targeted only if its span contains the target: a method without a result type has its body typed *ahead* by its completer when an overload resolution elsewhere needs its type, under whatever target that request has, and the typed-ahead body is cached and reused when the method is later typed with a target inside it; the first version stubbed every statement of such a body (finding I21). The same rule holds for templates and packages: a class typed off the path, such as the synthetic class of a refinement type or an anonymous class inside an expression a completer types ahead, is typed whole, since its members were skipped and lost (finding I25, `Sel { def foo2: Int }` collapsed to `Sel`). `Run.targetedStatsOwner` marks the one list `typedPackageDef`, `typedClassDef` or `typedBlockStats` is about to type, and `typedStats` consumes the mark, so a nested list is never mistaken for its parent's. The first version of the spike typed blocks whole after a mistake that lost `val x` from `locally { val x = 1; x@@ }`.

Why statements, not something finer: a statement is the unit the Namer and the Typer already agree on. Its symbols are entered before any statement is typed (`index`), with completers that type ahead only what a signature needs, so a skipped statement's symbols are as usable as a typed one's: the same name resolution, the same implicit search, the same `children` of a sealed class (registered by completers, `Namer.addChild`). What a skipped statement lacks is only its typed tree: diagnostics inside it, and the tree-based services (hover on a body, the scaladoc template of the *following* def, an auto-import's insertion point computed from the typed tree's shape). The whole-file providers of the presentation compiler keep using `run`; only `CompletionProvider` uses `runUpTo`, and `CachingDriver` serves a partial run to nobody (`isFullyTyped`).

What the first, prefix-based version of this spike got wrong, in hindsight: stopping *after* the target's top-level statement still typed everything before it, in full, and the x-ray made that visible: a completion in object 7 showed the bodies of `method1`…`method6` typed, explicit result types notwithstanding. The prefix was never the point; the typed *set* is.

## 3. The session: one run, many requests

`InteractiveDriver.runUpTo(uri, source, target)` keeps one `Session` per driver: the run, the compilation unit (whose `tpdTree` holds the typed part of the tree), the list of skipped statements, the diagnostics so far. A request on the same content (`textContent` equality) is answered by cases:

- **Served.** No skipped statement contains the target: nothing is typed (the x-ray's outcome `served`). The completion provider walks the typed tree to the target as before.
- **Resumed.** A skipped statement contains the target: it is typed by `typedStats(stat :: Nil, owner)(using ctx)` with its recorded context and owner, in the same run, with the request's target set so that the statement's own members are subject to the rule in turn (a resume into object 59 types `giant` and skips its siblings). The result is spliced into the typed tree in source order (a `TreeMap` that copies the path to the owner's `PackageDef` or `Template`), `SetRootTree` is re-run so that top-level classes point at their new root trees, and the newly skipped statements join the list.
- **Fresh.** Different content, or no session: a new targeted run.

Why the recorded context is enough: a statement's context in `typedStats` is the template's or package's context plus the imports typed before it, and nothing else that typing an earlier sibling would have added (a block's `NotNullInfo` threading is the exception, and blocks are not subject to the rule). So typing a statement later, after its siblings, in that context, gives the typed tree the in-order traversal would have given. The suite's `resume-in-the-same-run` types object 200 after object 10, then object 5: the set is not a prefix.

What keeps the run's state valid across requests: `cleanup` no longer errors out the completers of a partial run (`errorOutCompleters = !partial`); the run is the same `Run`, so `TyperState`, the implicit caches, uniques and the `ContextBase` are all the ones the typed trees were built with. This is what the fresh-run design throws away each time and the model calls the per-run facts; stage 3 (facts that outlive runs, [track-i.md](track-i.md) §6) is the step after this one.

**What an abort keeps.** The aborted run's trees and units are discarded and the previous run's stay current, but the aborted run's *context* stays current: the run brought the classpath denotations it touched forward to its own run id, and a query under the previous run's context finds them "invalid in run" (finding I14, found by the soak suite; the first version restored the previous context and the presentation compiler never noticed because `CachingDriver` starts a new run after an abort). The symbol table's clock does not roll back with the context.

**Leaving a file.** The symbols of skipped statements keep Namer completers of the run that indexed them, and a Namer completer refuses to run in a later run (`UnspecifiedErrorType`, finding I7). A whole-file run never exposed this because it completed every member while typing the bodies; the targeted run does, as soon as a request on *another* file refers to a member of this one: hovering in `QuotesAndSplices.scala` after a hover in `Applications.scala` gave `Not found: typedApply` (finding I17, found with the x-ray's hover mode). So before a request leaves a file, the driver completes every symbol of its skipped statements, in its own run (`completeSymbolsOf`): the signatures, with their type-ahead, not the bodies, deferred until the file is actually left. (The typed statements completed theirs as they were typed, and typing consumed their `ExpandedTree` attachments, so the walk is over the skipped list; an `ExpandedTree` can lead to a thicket that contains the tree itself, and the first version of the walk overflowed the stack on it, so each tree is visited once.) The honest statement of the rule: a run's lazy facts must be forced or discarded before the run is left, until completers become functions of node and owner (stage 3).

**Poisoned statements.** Typing consumes the untyped tree: `retrieveSym` takes `SymOfTree`, `typedUnadapted` takes `TypedAhead`, `traverse` takes `ExpandedTree`, the nested typers go (finding I8). A statement whose typing was unwound by a cancellation can not be typed again in that run. The driver re-parses the file, finds the statement with the same span and class, unlinks its symbols from the owner's scope (the package class or the enclosing class), indexes the fresh tree in the recorded context, and skips it again. References typed earlier keep the old symbols, which is sound for the typed trees (they are values) and wrong only in that a later request inside the replaced statement sees new symbols; nothing compares them. The suite covers the top-level case (`cancel-inside-a-statement`: object 300 with a 200-statement method) and the member case (`cancel-inside-a-member`: the method alone, typed by a resume). Only definitions are replaceable, and not a class or object whose companion is in the same owner and file: the synthetic members a case class gives its object (`apply`, `unapply`) are merged into the object's *tree* by the class's desugaring, and a fresh parse of the object alone lacks them (finding I22, `SourceTree(imp, sourceFile)` failed with "object SourceTree does not take parameters"). An aborted expression statement, the synthetic `<file>$package` object, or a companion marks the session poisoned, and *every* later request starts fresh: the aborted statement is neither typed nor skipped, so a request in its range would otherwise be served from a tree that holds nothing there (finding I23).

**The soak suite** (`CompletionSoakSuite`): on two files (forty objects with a 120-statement method; the shapes the wider suites tripped on: enum cases as children of a sealed trait elsewhere, a case class with an explicit `apply`, an extension block, givens, a nested package clause, blocks, inferred types across statements) a seeded random sequence of 300 targeted requests, cancellations at a random typer checkpoint (the checkpoint every 16 trees, `Run.typerCheckpointMask`, so that they land inside small statements) and edits, on one driver, must give at every completion point the completions a fresh whole-file run gives, and leave no symbol of the file `Touched`. Two seeds per file; on the objects file 30–39 cancellations land per run of 300 steps. It found I14 on its first run.

**The oracle suite** (`SessionOracleSuite`): the soak suite's points are hand-placed completions in generated files, and three bugs of the block rules (I20, I21, I23) sat in shapes nobody had placed a point in: a `while` body, a pattern, a method body typed ahead. The oracle suite takes real files (four of the compiler's own sources: `ByteCodecs`, `SourceTree`, `Chars`, `SimpleIdentityMap`, typed against the test JVM's classpath as the x-ray does) and hovers at the end of *every identifier* the scanner finds, 300 requests per seed in a shuffled order on one driver, a cancellation every seventh request, and after each request three re-checks of earlier offsets; each answer (the innermost typed tree at the offset: its class, span, type and symbol) must be the one a fresh whole-file run gives. It caught I20 within three to twelve requests on every file, then I21, I22 and I23 one after another as each fix exposed the next, and it logs the invariant that localizes them: after a request, no skipped statement may still contain the target. A run of the six tests takes about ten seconds.

Through the presentation compiler's `complete` rather than the driver, each request on the 400-object file costs 115–176 ms however little the driver types (the suite's `resume-in-the-same-run`: 1 ms of driver time inside 150 ms). The compiler is no longer where a completion's time goes; where it goes in mtags is unmeasured (finding I12).

## 4. Cancellation that unwinds

**The problem it solves.** The stock `InteractiveDriver` reports cancellation to the compiler through a `ProgressCallback` whose `isCancelled` is `Thread.interrupted()`: the bit is consumed by the first check and never set again, the typer never polls it, and `Run.isCancelled` only degrades (a `WildcardType` for the rest of the run, which a completion in progress can store into a classpath denotation that outlives the run). Metals' cancel token therefore cancelled the *future* and never the *work*: a completion made obsolete by the next keystroke ran to the end, and the next one waited behind it.

**The design: abort and restart.** A cancellation sets a sticky flag on the driver (`cancel()`, or a per-request checker installed by `withCancelChecker`). `Typer.typed` polls it every 1,024 typed trees (`Run.checkCancelledTyping`, `Run.typerCheckpointMask`), in `Mode.Interactive` only, and throws `CompilationUnit.CancelledCompilation`, a `ControlThrowable` whose cause is a `CancellationException` so that mtags classifies it as a cancellation. The exception passes through every handler on the way out (the two catch-alls in the completion code became `NonFatal`), through `completeFrom`, the symbol loaders and the lazy annotations, each restoring what it had set, out of `compileSources`, through `InteractiveDriver.run` and `CachingDriver.run` (which does not count the run as compiled), to `CompilerAccess.withSharedCompiler`, which answers the request's default and keeps the driver. Batch compilation is untouched: there a cancelled run skips its remaining units, as before, and sbt sees a run that ends normally.

**What survives an abort, by kind of state:**

- *Facts.* Denotations are written on completion only. `completeFrom` clears `Touched` on a symbol whose completion the exception unwound (an incomplete symbol is otherwise a cyclic reference for the rest of the run); a `LazyAnnotation` keeps its thunk; a `SymbolLoader` leaves the root to be loaded again instead of marking it absent. The next run recomputes them.
- *Trees and units.* Immutable; the aborted run's partial tree is garbage. The driver keeps the previous run's trees and units current, and the *aborted* run's context: the run brought the classpath denotations it touched forward to its own run id, and a query under the previous run's context would find them "invalid in run" (finding I14, found by the soak suite; the first version restored the previous context and the presentation compiler never noticed because `CachingDriver` starts a new run after an abort). The symbol table's clock does not roll back with the context.
- *Unit-scope state and diagnostics.* Per `Run`, dropped whole with it; the next run regenerates the diagnostics because it re-enters the file.
- *The session.* A cancellation during a resume keeps every statement typed before it; the one being typed is re-parsed and re-indexed (§3, poisoned statements). A cancellation during a fresh run discards that run whole.

**The token path.** Metals' `CancelTokens` turns lsp4j's cancelled future into the `CancelToken` of `CompilerOffsetParams`; mtags' `CompilerAccess.withInterruptableCompiler` runs the request with it; the patch's `Scala3CompilerAccess` installs `token.onCancel()` as the driver's checker for the duration of the request. `CompletionAbortSuite.abort-via-token` is this path end to end without the editor: a token cancelled 20 ms after submission on a file whose typing takes longer, the request answers the default, the driver is not recreated (the run id grows by exactly one on the next request), the next completion on the file is whole.

**What the spike found.** A cancellation noticed *before* the typer made `tryEnterUnit` skip the unit, and the driver then failed on an empty unit list, which mtags would have treated as a crash: the driver now checks the callback after `compileSources` and throws the same exception. `Compiler.newRun` resets the `ContextBase` before the run starts, so after an abort the previous run's trees are not servable from `CachingDriver`'s cache: a cancelled run invalidates it. A symbol of the sourcepath first touched in the aborted run and completed in the next gets `UnspecifiedErrorType` from its Namer completer (finding I7; the same mechanism as I17 in §3). The typer's checkpoint never polls inside implicit search (finding I11): a 229 ms search of sixty nested givens saw zero polls, and a tick in `filterMatching` and `typedImplicit` would be needed to cancel a request stuck there; that checkpoint was built and measured in a separate spike and is not part of this patch.

**Not done this way:** nested servicing with taint (IntelliJ's rule: answer "unknown" for a `Touched` symbol inside the run and cache nothing above it) is sound over facts but needs every non-fact mutation to be read-only when tainted, which in dotc means the namer's scope entries and the run's reporter; and building on thread interrupts, which every reason the survey found for "cancellation never arrives" argues against (the bit is unsticky and consumed, `ClosedByInterruptException` in a loader becomes `InterruptedException` with `markAbsent` in the `finally`, and the catch-alls swallowed it).

## 5. The x-ray and the latch

[`XrayServer.scala`](../probes/interrupt/xray/XrayServer.scala) drives one `InteractiveDriver` from a page: per request the run id, the typed statements (and the skipped members inside them), where a cancellation unwound, `Run.typedTreeCount`, wall time, the number of symbols of the file still `Touched` afterwards. For a deterministic cancellation the generated file's last object has `def giant` whose first statement is `tests.macros.Latch.await`, a `transparent inline` macro (expanded at typer, so while the statement is being typed) that blocks while a latch file exists. A "latched" request arms the file; the page shows the typer blocked at the macro with the tree count so far; "Cancel" sets the driver's cancel flag and removes the file, so typing continues to the next 1,024-tree checkpoint, inside `giant`, and unwinds there; "Release" lets it finish. The stories on the page (session, cancel, edit, whole file) state what the design predicts before each step and check it against what the driver reported. An explorer panel lists a snapshot of `compiler/src/dotty/tools/dotc` at the base commit, and a file from it is typed against the compiler's own classes (the whole test JVM's classpath): on `Typer.scala` a completion inside `typedSelect` is a fresh run of 1,362 trees in 450 ms cold (the imports, `class Typer` with 129 of its members skipped), and the next request in the same method is served in 44 ms with twelve `is…` members of `Context`.

## 6. Graceful degradation in interactive mode

Built on 22 Oct 2026 after the measurements below; the design as first written follows, with what each rule became.

### What goes wrong today

dotc's laziness has one recursion guard: `SymDenotation.completeFrom` sets `Touched` before running a completer and throws `CyclicReference` if it finds the flag already set. In batch compilation that is right: a true cycle is an error, and `Namer` and `Typer` catch the exception where an alternative exists (a missing result type, a self-reference through an implicit) and report it. In the presentation compiler it has three consequences the editor does not want:

1. **The request fails whole.** A cycle met while completing one symbol, say while computing the type of one of two hundred completion candidates, unwinds the request through `CompletionProvider`, which answers with nothing (the `catch NonFatal` in `Completions.scala` guards one site; most are unguarded). The same for a `StackOverflowError` (a 400-deep chain of selections overflowed the test thread while this spike was built) and for an `AssertionError` in a tree the targeted run left partial.
2. **The failure leaks.** When the exception unwinds through `completeFrom`, `Touched` stays set on every symbol on the completion stack unless a handler clears it. The cancellation patch clears it for `CancelledCompilation` only (`untouchIfIncomplete`); a `StackOverflowError` or an assertion leaves the symbols as cyclic for the rest of the run, which with a session is the rest of the editing of that file.
3. **The degraded value is cached as if it were right.** Where dotc does recover (`Namer.Completer.complete` gives the symbol `UnspecifiedErrorType`, `Namer` reports "overloaded or recursive method needs result type" and gives an error type), the error type is the symbol's info from then on. For a symbol of the file that is per run, so the next fresh run recomputes it; in a session the run is long-lived, and for a classpath or sourcepath symbol the denotation outlives runs anyway (finding I7's `greetAlpha: Any`).

### What IntelliJ does

IntelliJ's `RecursionManager` ([`RecursionManager.java`](https://github.com/JetBrains/intellij-community/blob/master/platform/core-api/src/com/intellij/openapi/util/RecursionManager.java), used by every lazy resolve in the Scala and Kotlin plugins) is the same guard with four rules attached, worth borrowing as a set:

1. **Prevention returns, it does not throw.** `guard.doPreventingRecursion(key, memoize, computation)` returns `null` when `key` is already being computed on this thread. The caller degrades at the smallest granularity it can: this one type is `Any`, this one candidate is dropped, this one reference is unresolved; the enclosing computation continues and the user sees a partial answer rather than none. The thrown exception is reserved for genuinely unrecoverable situations.
2. **A prevented result is poisoned, and so is everything computed on top of it.** `RecursionManager.markStack()` before a computation and `stamp.mayCacheNow()` after it say whether any prevention happened beneath; if one did, the result must not be stored in a cache that outlives the computation (`CachedValuesManager` checks this itself). `guard.prohibitResultCaching(key)` is the explicit form. The rule exists because a prevented recursion gives whichever frame happens to be the outermost its *provisional* value, so what was computed from it is right only for this demand order; finding I4 shows the cached root depending on that order when the rule is bent.
3. **Memoization inside the re-entered frame is scoped to the outer computation.** With `memoize = true`, values computed between the re-entry and the outer frame's completion are kept only until the outer frame finishes (they are replayed if the same key is asked again meanwhile), then discarded. This is the "memoized" nuance the Lean model's `psi` mode captures.
4. **Tests assert on preventions and missed caches.** `RecursionManager.assertOnRecursionPrevention` turns every prevention into a test failure, and `assertOnMissedCache` fails a test that caches a value without a `markStack`/`mayCacheNow` check; both are how the plugins find the sites that violate rules 1 and 2.

### Mapping onto dotc, in interactive mode only

The key is the symbol; the stack marker is `Touched`; the prevention is the `CyclicReference` thrown by `completeFrom`. The proposal keeps dotc's protocol, since the handlers that catch `CyclicReference` to choose an alternative are part of the language's error behaviour, and adds the four rules around it under `Mode.Interactive`:

- **Degrade at the request's call sites, not inside the compiler.** The presentation compiler's providers compute per item (each completion candidate's type and label, each signature, each hover): wrap each item, not the request, in a handler that drops the item on `CyclicReference`, `StackOverflowError` or an assertion and records the failure on the run. A completion that lists 199 of 200 candidates is the IntelliJ outcome; today's is 0 of 200. The compiler side needs nothing for this.
- **Clear `Touched` on every unwinding exception, not only cancellation.** `untouchIfIncomplete` in `completeFrom` for any `Throwable` other than `CyclicReference` itself (which must keep the flag on the symbol that is actually cyclic, since batch compilation's error messages depend on the second encounter), guarded by `Mode.Interactive` so that batch compilation keeps its current behaviour. This is rule 2 at the one place dotc has a stack.
- **Taint, do not cache.** The run records every prevention (`Run.preventedCycles`, the symbols on the `Touched` stack at the moment of the throw). A symbol that received a degraded info while a prevention was below it (the `UnspecifiedErrorType` and "needs result type" cases) is *tainted* for the run. Within a request the tainted info is used, as today. Across requests the session may not keep it: the simplest sound rule is that a request that recorded a prevention marks the session poisoned, so that the next request starts a fresh run, which recomputes every per-run fact from scratch. A fresh targeted run is now cheap (43 trees for the x-ray's file), which is what makes the simple rule affordable; a finer rule (reset only the tainted symbols' infos to their completers) is blocked by I8's consumed attachments, the same obstacle as a poisoned statement, and would need the non-destructive attachments of stage 3.
- **Symbols that outlive runs.** A classpath symbol's `SymbolLoader` can be re-run (the cancellation patch already leaves the root to be loaded again); a sourcepath symbol's `Namer` completer can not (I7). Tainted infos on those must be reset at the end of the request: loaders by `untouchIfIncomplete` and `info = completer`, Namer completers by re-entering the sourcepath file in the next run, which is I7's open item and is unchanged by this design.
- **Memoization scope** (rule 3) is the run itself: a session's run is the outer frame, and the poisoned-session rule discards everything memoized inside it. Nothing finer is proposed.
- **Assertions in tests** (rule 4): a `-Yinteractive-assert-no-cycles`-style flag, or a test-only hook on `Run.preventedCycles`, that fails `CompletionSuite` and friends on any prevention, to find the completions that today silently return nothing.

What this does not change: the batch compiler's behaviour (every rule is under `Mode.Interactive`), the messages dotc reports for true cycles (the throw is kept), and the semantics of a request that meets no failure.

### What was measured

- **Cycles on real code are rare.** `CycleMeasureSuite` runs targeted completions at every 40th identifier of this checkout's `Typer.scala` (5,575 lines, 768 completions, 3 runs, 3.8 s in all with the first run at 2.5 s) and `Namer.scala` (2,353 lines, 306 completions, 1 run, 289 ms), against the compiler's own classes: one cyclic reference prevented (a type parameter `U`), no completion unwound, no request failed. Over the whole presentation-compiler suite the process-wide counter (`-Ddotty.interactive.cycleStats=true`, `Run.CycleStats`) is in the register.
- **The provider already degrades per item for member completions.** `CompletionDegradeSuite.a-leaked-touched-flag-costs-one-item` plants a leaked `Touched` flag on `pBeta` of `object Leak` (a `LazyType` info and the flag, as an exception unwinding through its completer left it before this change) and completes `Leak.p`: the answer is `pAlpha, pGamma`, not nothing. `Completions` wraps the places that read a candidate's info in `NonFatal` handlers, which catch `CyclicReference` (a `TypeError`, an `Exception`). What those handlers do not catch is a `StackOverflowError`, and what nothing handled was the state left behind: the request after the leak would have met it again, in the same run, forever.
- **A true cycle costs its members only.** `a-true-cycle-costs-the-cyclic-members-only`: `def pBeta = pGamma; def pGamma = pBeta` lists as `pBeta: Any, pGamma: Any` beside the whole `pAlpha` and `pDelta`; `Namer` reports the cycle and gives the error type, as in batch compilation.
- A fresh targeted run is 43 trees on the x-ray's file and 2 top-level trees on the suite's 400-object file (§3): cheap enough for the taint rule.

### What was built

- **`Run.cyclesPrevented`, `Run.leaksHealed`, `Run.completionsUnwound`.** `completeFrom` records on the run, in interactive mode, every cyclic reference it prevents, every stale flag it heals, and every completion an exception other than a cyclic reference or a cancellation unwinds through. `Run.isTainted` is the last of these; `InteractiveDriver.isTainted(uri)` exposes it, and the x-ray shows it.
- **A stale `Touched` flag is healed, not reported.** The run keeps the set of symbols whose completion is in progress (`Run.completing`, pushed and popped in `completeFrom`, interactive mode only). A flag found set on a symbol not in that set is what an earlier unwind left, not a cycle: `completeFrom` clears it, completes the symbol, and records the healing. This is rule 1 at the one place dotc decides between "cycle" and "in progress": `a-leaked-touched-flag-costs-one-item` plants such a flag on `pBeta` and gets `pBeta` completed, with `pAlpha` and `pGamma`, where the request before this change dropped it.
- **`Touched` cleared on every unwinding exception in interactive mode** (`unwindsInteractive` in `completeFrom`): a cancellation in any mode, as before; in interactive mode also a cyclic reference unwinding through an *outer* completion (the result of a computation that met a cycle below it is not kept: `mayCacheNow`), a stack overflow, an assertion. The exception itself still propagates: the request degrades where it is handled, and the symbol is completable again afterwards. Batch compilation is unchanged.
- **Taint, narrowly.** The first version tainted the run on any prevented cycle and started a fresh run for the next request. The caching suite showed why that is wrong: an ordinary member completion such as `1.` prevents cycles inside the provider's own type-ahead of implicit conversions (over the whole suite, 223 preventions, on the type parameters `F`, `E`, `T_SPLITR` of collection methods), all caught by `Completion.scala`'s fallback; tainting on them would have discarded the session after most member completions. With the flags cleared on the way out, a prevented cycle leaves the run as it was; only an exception of unknown effect (`completionsUnwound`) taints, and `runUpTo` then starts a fresh run instead of resuming. `a-true-cycle-costs-the-cyclic-members-only` checks that a true cycle in the file is served by the same run with the same answer.
- **Not built:** handlers beyond what `Completions` has (a `StackOverflowError` is caught by nobody on either side; a bounded `-Xss` for the compiler job thread is Metals' call), and the test-time assertion on preventions (rule 4): `Run.CycleStats` counts, nothing fails on them yet.

## 7. Integrating the PoC into a Metals / VS Code workflow

What is already wired, and what a real session with VS Code needs.

**The cancel token path is complete.** VS Code sends `$/cancelRequest` for a completion the moment the user types again; lsp4j cancels the request's `CompletableFuture`; Metals' `CancelTokens` turns that into the `CancelToken` it passes in `CompilerOffsetParams`; mtags' `CompilerAccess.withInterruptableCompiler` runs the request on the compiler job queue with that token; the patch's `Scala3CompilerAccess.withInterruptableCompiler` installs `token.onCancel()` as the driver's cancel checker for the duration of the request; the typer's checkpoint (every 1,024 trees, `Run.typerCheckpointMask`) polls it, unwinds with `CancelledCompilation`, whose cause is a `CancellationException` so that mtags classifies it as a cancellation and keeps the compiler instance (`CompletionAbortSuite.abort-via-token` is this path end to end, without the editor). Nothing in Metals itself changes.

**Steps to try it in VS Code:**

1. Publish the patched compiler locally from the scratch worktree, module by module (`scala3-compiler-bootstrapped`, `scala3-presentation-compiler`, their dependencies `scala3-interfaces`, `scala3-library-bootstrapped`, `tasty-core-bootstrapped`, `scala3-directives-parser-bootstrapped`, and `scala3-sbt-bridge-bootstrapped` for the build import), each with `Compile / packageDoc / publishArtifact := false` and, for `scala-library-bootstrapped` and the presentation compiler, `Compile / doc / sources := Seq()`: the aggregate `scala3-bootstrapped/publishLocal` runs scaladoc, whose snippet checker fails on a reference page and whose run over the Scala 2 library runs out of memory. The artifacts land under `~/.ivy2/local` as `3.10.2-RC1-bin-SNAPSHOT` (the build's `baseVersion` at `d168df2a76`), which coursier, and so Metals, resolves.
2. A sample project, [`probes/interrupt/metals-demo`](../probes/interrupt/metals-demo/build.sbt): `scalaVersion := "3.10.2-RC1-bin-SNAPSHOT"`, `scalacOptions += "-Yinteractive-log"`, and the x-ray's generated 60-object file as its source. Metals fetches the presentation compiler of the project's Scala version through coursier, here the local one, and runs it in its own JVM with the project's `scalacOptions`, so the two settings of this spike reach the driver as options: `-Yinteractive-log` prints one line per request to stderr, which Metals writes to `.metals/metals.log` (`[dotc-session] runUpTo A.scala@1137 fresh run=4 typedTop=2 skipped=60 trees=43 4.1 ms`), and `-Yno-targeted-requests` turns targeting off for an A/B.
3. Observe: in VS Code, View > Output > Metals, or `.metals/metals.log`; a thread dump of the Metals process during a long completion shows `checkCancelledTyping` on the compiler thread; typing quickly over a completion popup exercises `$/cancelRequest`. Without an editor, [`metals_lsp.py`](../probes/interrupt/metals-demo/metals_lsp.py) drives Metals over stdio on the sample project (initialize, open the file, completion, hover, definition and signature help at a few positions) and prints the `[dotc-session]` lines its log collected; `coursier fetch org.scalameta:metals_2.13:1.6.9` gives the classpath to launch it with `scala.meta.metals.Main`.
   Done on 22 October 2026 with Metals 1.6.9: it imported the build through sbt and Bloop in 18 s, resolved the presentation compiler of the project's Scala version from `~/.ivy2/local`, and answered completion, hover, definition and signature help at three positions in about 0.2 s each; its log holds 17 `[dotc-session]` lines, the first a fresh run (`[dotc-session] runUpTo Main.scala@9 fresh run=3 typedTop=2 skipped=0 trees=22 117.7 ms`), the rest 1 resumes and 10 served, one run for the whole session. VS Code is not installed on this machine; with it, the same project opened with the Metals extension gives the same log under View > Output > Metals.
4. Which requests are targeted: completion, hover, definition and type definition, signature help and the expected type at a position go through `runUpTo` at the request's offset, then read the typed tree, the same shape in each provider. The gate is the compiler setting `-Yno-targeted-requests` (passed to the presentation compiler like any other option): with it every `runUpTo` is a `run`, the whole file typed per request as before the spike. Two providers read the typed tree of a definition the request refers to (go-to-definition locates a same-file symbol by its `DefTree`; signature help prints an erroneous return type from `defTree.tpt`), which a skipped statement lacks: `InteractiveDriver.typeDefinitionOf(uri, sym)` resumes into that statement on demand, and the providers call it before reading (finding I26). References, semantic tokens, inlay hints, semanticdb, the code actions and the diagnostics `didChange` reports stay on `run`, through `CachingDriver`, which never serves a partial run to them (`isFullyTyped`): their answers are about the whole file, or a range of it.
5. What a user would notice: the first completion in a big file costs a parse, an index and the path to the cursor rather than the whole file; later completions in the same unedited file are answered from the run; a completion cancelled by further typing no longer blocks the next one behind a run that cannot stop. What they would not notice yet: the per-item degradation of §6, and the 115–176 ms the presentation compiler spends around the driver on the 400-object file (I12), which caps the gain.

**Checkpoint interval.** `Run.typerCheckpointMask` is a process-wide knob (1,023 by default, a checkpoint every 1,024 typed trees). The soak suite sets it to 15 so that cancellations land inside the small statements a targeted run types; for Metals the default stands, and whether a finer interval is worth its cost (a counter increment per typed tree is already paid; the poll is a volatile read of the token's future) is a measurement to make on the implicit-search-heavy files of finding I11.

## 8. Prior art

- scalac's `typedStats` with `unit.targetPos`: sibling statements that do not include the target are returned untyped ([`Typers.scala`](https://github.com/scala/scala/blob/2.13.x/src/compiler/scala/tools/nsc/typechecker/Typers.scala), `typedStat`'s `localTarget` branch). The rule in §2 is that rule, applied through the context recording that makes a later resume possible, which scalac does not have: its targeted typecheck (`typedTreeAt`) is per request, with `Global`'s `typerRun` and `unitOfFile` as the session.
- IntelliJ's `RecursionManager` (§6), and `CachedValuesManager`'s dependency on `mayCacheNow`.
- Kotlin's `LazyResolveToken`/`ResolveSession` in the K1 frontend: resolve per declaration on demand with a session per module, no typed-tree splicing (bodies are resolved into a `BindingContext` keyed by element).
- The Lean model: [`Interrupt.lean`](../../query/Query/Interrupt.lean) for abort and `Touched` ([`abort_touched`](../../query/Query/Interrupt.lean#L269), [`touched_stays_cyclic`](../../query/Query/Interrupt.lean#L287)), its `psi` mode for rule 3, finding I4 for what bending rule 2 costs; [`Revision.lean`](../../query/Query/Revision.lean) for the facts-that-outlive-runs step this session is the precursor of.

## 9. Which findings are general

Not all of the register's rows are about this spike. Sorted by what they affect before any of it:

Checked on an unmodified checkout at the base commit with [`StockFindingsSuite`](../probes/interrupt/xray/StockFindingsSuite.scala) (copied beside the x-ray; it runs in `presentation-compiler/test` of a stock worktree): the two candidates that looked general were not.

**The stock compiler and Metals today.**
- I7, *not* as first described: a sourcepath member first completed in a run later than the one that entered it is typed correctly on stock (`greetAlpha: Int`; the loader re-enters the file per run). The `UnspecifiedErrorType` is reached only when an abort unwinds through the entering run, which leaves the file's Namer completers behind. Stock mechanism, reached by the spike.
- I10: the run id is 16 bits and nothing guards it; a long-lived driver overflows it into the phase bits.
- I11: nothing polls for cancellation inside implicit search; before the spike nothing polled anywhere in the typer, so this is one instance of the general one (the stock driver's cancellation consumes the interrupt bit and never unwinds, §4).
- I12: a completion through mtags costs 115–176 ms on the 400-object file however little the compiler does; whole-file runs hide it behind the compile.
- I15: an empty completion prefix uses `freshDriver()`, so the most common member completion never benefits from the caching driver.
- I16, the leak half, *not* reproduced on stock: after a `1.` completion no member or type parameter of `List`, `IterableOnceOps`, `IterableOnce`, `IterableOps`, `RichInt`, `StringOps`, `StepperShape` or `Stepper` is left `isCompleting`, and a second completion lists the same 184 items. The 172 preventions the patched suite counts may be of the patched build's own making, or on symbols that scan does not reach; open.
- I4 (IntelliJ) and I1, I2 (scalac) are general to their compilers, from the earlier phases of Track I.

**Consequences of targeting, resumption or abort, which a whole-file run per request never meets:** I8 (an untyped tree is consumed by typing), I13 (four facts obtained from typing a sibling), I14 (the restored context older than the symbol table after an abort), I17 (skipped statements' completers in a later run), I19 (spans compared across sources), I20 and I23 (the session's bookkeeping of what is typed and what is skipped), I21 (a body typed ahead under another request's target), I22 (a replaced tree loses what another tree's desugaring merged into it). Each is a design constraint on any resumable or targeted typer rather than a bug in the current one; I18 is open and may belong to either list.

## 10. Open questions

- The suite found three services that read the typed tree's shape rather than symbols: the scaladoc template of the following definition (handled by scalac's whole-list rule), the auto-import insertion point (handled by never skipping package clauses), and whatever the remaining failures of the wider completion suites turn out to be (the register has the current state). Each is a place where "the typed tree is a value" is less true than it looks: the tree's *shape* is consulted as state.
- A resume types a statement whose siblings were typed in the same run but earlier: the `TyperState` and constraint state are not threaded between top-level statements today either, but a nested statement's `NotNullInfo` is; the rule excludes blocks for that reason, and whether any template-level state is threaded in a way a later resume would miss is checked only by the suites.
- `typedPrefixLength` is a misnomer now (it counts the typed top-level trees, not a prefix); it stays for the tests and the x-ray until the API is settled.
